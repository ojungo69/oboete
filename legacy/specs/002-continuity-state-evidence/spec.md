# Feature Specification: 継続状態に証跡の置き場を作る（Cluster C）

**Feature Branch**: `feat/continuity-state-schema-v2`

**Created**: 2026-08-17

**Status**: Draft

**Input**: User description: "continuity 状態 schema の拡張（Cluster C: #35 / #43 / #44 / #39）。凍結されている CanonicalWorkStateV1 / PendingOperation を 1 回でまとめて拡張し、addendum v6.2 §4.3 が課す 3 つの検査と、退避・孤児 terminal の証跡を「状態だけを渡された実装」でも満たせるようにする。"

## 背景と問題

addendum v6.2 §4.3 は terminal event に 3 つの条件を課している。

1. 権威順序で start より後であること
2. 未適用であること
3. payload / source hash が衝突しないこと

いま参照実装がこの 3 つを満たせているのは、**状態の外側に索引を持っているから**である。
権威順序は `operationStarts`（凍結 schema の外にある `operationId → ingestSeq` の写像）で見て
おり、冪等台帳が適用済みの指紋を持っている。daemon は event store を持つのでこの索引を作れる。

一方 **状態だけを受け取った実装**（別言語の参照実装、checkpoint からの復元経路、状態を配って
判断させる将来の経路）は同じ索引を作れない。同じ状態と同じ event を渡しても、daemon と別実装で
**受理・隔離の判断が割れる**。判断が割れれば状態も `stateRevision` の連鎖も内容 hash も割れる。

同じ根で、証跡の**置き場が無い**ものが 2 つある。

- §4.3 は「候補 0 件または複数の terminal は unmatched evidence として保存する」と書いているが、
  候補 0 件のときは足す相手（`PendingOperation`）が存在しない。参照実装は保存できないので隔離を
  選んだ（`terminal_orphaned`）。正本の文面と実装が食い違ったままになっている。
- 上限 256 件で退避した operation は状態から消える。退避したこと自体は診断に出るが、状態には
  何も残らないので、状態を後から見た人には「その operation が存在した」ことすら分からない。

Cluster C は、この 4 件（#35 / #43 / #44 / #39）を**凍結 schema の 1 回の拡張**でまとめて閉じる。
凍結 schema の変更は版・fixture・hash・別言語実装の期待値に波及するため、小刻みに繰り返さない。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 状態だけで権威順序を判定できる (Priority: P1)

別実装が「状態 1 つと event 1 つ」だけを渡され、terminal を受理してよいかを判断する。いまは
start がどの取り込み連番で来たかが状態に無いため、権威順序の検査ができず、時刻で代用するか
検査を省くしかない。時刻での代用は §4.3 が明示的に否定している（`occurredAt` は adapter 由来で
単調とは限らない）。

**Why this priority**: 3 つの検査のうち、状態だけでは**原理的に実施不能**なのはこれだけ。他の 2 つは
劣化した判断で済むが、これは判断そのものができない。別言語実装のパリティを名乗れるかがここに
かかっている。

**Independent Test**: 状態と event だけを渡す経路に、start より前の連番を持つ terminal を与える。
event store も外部索引も渡さずに、その operation が閉じずに `unknown` へ倒れ、順序違反の診断が
出れば合格。

**Acceptance Scenarios**:

1. **Given** start が連番 100 で受理された operation を含む状態、**When** 連番 50 の terminal を
   状態だけを持つ実装に渡す、**Then** その operation は閉じず、`terminal_out_of_order` の診断とともに
   `unknown` へ倒れる（配送鍵は消費される）。**隔離ではない**: 正本 §4.3 が隔離を課すのは
   correlation / hash の衝突で、順序違反は「閉じられない」側の規則（「zero か複数の open に
   マッチした terminal は何も閉じず、候補を `unknown` にして診断を出す」）に落ちる。連番の
   前後関係は event と状態だけで決まる定常的な性質なので、隔離すると配送鍵が消費されないまま
   同じ判定が毎回返り、adapter は無限に再送する
2. **Given** 同じ状態、**When** 連番 150 の terminal を渡す、**Then** operation が閉じる
3. **Given** daemon（索引あり）と状態だけの実装に同じ状態・同じ event 列を渡す、**Then** 両者が
   同じ受理・隔離の判断に到達し、同じ状態と同じ内容 hash を出す
4. **Given** すでに pending にある operation へ **再配送の start** が届く、**When** それを適用する、
   **Then** 順序の材料は**最初に受理した start のまま変わらない**（再配送で上書きされない）
5. **Given** 順序の材料（`startIngestSeq`）だけを持ち turn 種別の材料を持たない復元状態、
   **When** `nativeOperationId` を名乗らない terminal を渡す、**Then** その operation は閉じず、
   `terminal_turn_unverifiable` の診断とともに `unknown` へ倒れる。terminal が名乗る
   `turnIdSource` は照合の片側でしかないので、状態側に材料が無い以上「一致した」とは言えない。
   同じ状態でも rule 1（`nativeOperationId` 一致）の terminal は turn 両立を要求しないので閉じる

---

### User Story 2 - 状態から消えた証跡が状態に残る (Priority: P2)

上限で退避された operation と、相手のいない terminal（孤児）が、状態の中に有界な記録として残る。
いまはどちらも診断に出るだけで、状態を受け取った側からは存在が消える。

**Why this priority**: 正本（§4.3）が「保存する」と書いている扱いを実装できるようにする。ただし
現状でも診断は出ており、誤った判断が確定するわけではないので P1 ではない。

**Independent Test**: 上限まで埋めた状態に新しい start を入れて退避を起こし、退避された operation の
識別子が状態の記録に現れることを確認する。孤児 terminal も同様に、記録に現れることを確認する。

**Acceptance Scenarios**:

1. **Given** `pendingOperations` が上限の状態、**When** 新しい start が届いて 1 件が退避される、
   **Then** 退避された operation の識別と状態が有界な記録に 1 件追加され、診断も出る
2. **Given** 開いている operation が 1 つも一致しない terminal、**When** それを適用する、
   **Then** 孤児として記録に残り、診断も出る
3. **Given** 記録自体が上限に達した状態、**When** さらに記録すべき事象が起きる、**Then** 記録の
   古い側（配列の先頭）が落ち、落としたことが診断に出る（黙って消えない）
4. **Given** 記録を持たない旧い状態、**When** それを読む、**Then** 読めて、現状と同じ扱いになる

---

### User Story 3 - 配送 ID をまたいだ payload 衝突を見つけられる (Priority: P3)

同じ operation に対して、成否が同じで payload だけが違う terminal が、別の配送 ID で 2 回届く。
いまは冪等台帳が別の論理 event として扱い、成否の比較も通るので、衝突として検出されない。

**Why this priority**: 現状で失われるのは「2 通目の payload が違った」という診断だけで、状態は
最初の terminal のまま変わらない。誤った成否が確定することはない。前提も corruption か
実装バグなので、優先度は最も低い。

**Independent Test**: 同じ operation を、同じ成否で、違う payload・違う配送 ID で 2 回 terminal し、
2 通目が衝突として扱われることを確認する。

**Acceptance Scenarios**:

1. **Given** `succeeded` で確定した operation、**When** 同じ成否・違う payload・違う配送 ID の
   terminal が届く、**Then** 衝突として隔離され、状態は変わらない
2. **Given** 同じ operation、**When** 同じ成否・**同じ** payload の terminal が別の配送 ID で届く、
   **Then** 適用済みの再配送として扱われ、隔離されない
3. **Given** 比較材料を持たない旧い状態、**When** 同じ状況が起きる、**Then** 現状と同じく
   適用済みの再配送として扱われる（新しい検査は材料が無ければ発動しない）

---

### Edge Cases

- 旧い状態（新しい欄を持たない）を読んだとき、新しい検査は**発動しない**。材料が無いことを
  「検査に合格した」と読み替えてはならない。現状の fail-closed 経路にそのまま落ちる。
- 再配送の start は順序の材料を書かない。書けてしまうと、遅れて届いた再配送で権威順序が後ろへ
  ずれ、正当な terminal が順序違反として落ちる。
- 記録の配列が上限に達したときの落とし方は、`pendingOperations` の退避と同じ規則にする
  （配列位置が権威、`startedAt` で並べ替えない）。ここで別の規則を作ると、実装ごとに
  違う記録が残って hash が割れる。
- 退避された operation の記録に、その operation の payload を持ち込まない。記録は「あった」ことを
  示すためのもので、内容の保管庫ではない（`sensitivity` の判断を記録側でやり直すことになる）。
- 記録が単調に増えることで、状態のサイズが上限を破らないこと。すべての新しい配列は
  §10 の `arrayItems` と同じ上限を持つ。

## Requirements *(mandatory)*

### Functional Requirements

**順序の材料（#35）**

- **FR-001**: 状態は、開いている operation ごとに「その operation の start を受理したときの
  取り込み連番」を保持できなければならない（MUST）。
- **FR-002**: 状態は、開いている operation ごとに「その start が名乗った turn 識別の由来」を
  保持できなければならない（MUST）。現行の外部索引が両方を持っており、片方だけでは
  §4.3 rule 2 の turn 両立条件を状態だけで判断できない。
- **FR-003**: 順序の材料は、**最初に受理した start** からのみ書かれなければならない（MUST）。
  同じ operation への再配送 start から上書きしてはならない（MUST NOT）。
- **FR-004**: 順序の材料を持たない operation に対しては、現行の fail-closed 経路と同じ扱いを
  しなければならない（MUST）。材料が無いことを検査合格として扱ってはならない（MUST NOT）。
  turn 種別の材料（`startTurnIdSource`）が無い場合、その候補を rule 2 の候補集合から除外しては
  ならない（MUST NOT。帰属を取り違えるため）が、rule 2 で閉じてもならない（MUST NOT）。
  operation は理由を名指しする診断とともに `unknown` に倒す（MUST）。閉じられるのは turn 両立を
  要求しない rule 1 だけである。

**消えた証跡の記録（#43 / #39）**

- **FR-005**: 状態は、上限で退避された operation の識別と最後に分かっていた状態を、有界な記録
  として保持できなければならない（MUST）。
- **FR-006**: 状態は、開いている operation に一致しなかった terminal を、有界な記録として
  保持できなければならない（MUST）。
- **FR-007**: 記録に payload・引数・出力を含めてはならない（MUST NOT）。識別と分類に限る。
- **FR-008**: 記録の配列が上限に達したときは、配列の先頭から落とさなければならない（MUST）。
  時刻で並べ替えてはならない（MUST NOT）。
- **FR-009**: 記録への追加、および記録からの脱落は、いずれも診断として報告されなければ
  ならない（MUST）。黙って消してはならない（MUST NOT）。

**受理済み terminal の指紋（#44）**

- **FR-010**: 状態は、確定した operation ごとに、受理した terminal の指紋を保持できなければ
  ならない（MUST）。
- **FR-011**: 確定済みの operation に対して、同じ成否・違う指紋の terminal が別の配送 ID で
  届いた場合、衝突として扱わなければならない（MUST）。
- **FR-011a**: 照合が open な候補を 1 件に決めた場面で、その候補が既に指紋を名乗っていて
  入ってくる terminal の指紋と食い違う場合、上書きせず衝突として扱わなければならない（MUST）。
  凍結 schema は `started` / `unknown` の要素が指紋を持つことを妨げないので、復元した状態では
  この形が生じうる。ただし入ってくる terminal が `unknown` に倒れる場合は発動してはならない
  （MUST NOT）——その経路は指紋を書かないので上書きが起きず、判定は event 自身の性質なので
  隔離するとその operation は永久に閉じられない。
- **FR-012**: 指紋を持たない operation に対しては、現行どおり適用済みの再配送として扱う
  （MUST）。新しい検査は材料が無ければ発動しない。

**互換性と版**

- **FR-013**: 新しい欄はすべて任意でなければならない（MUST）。既存の状態は、欄が無いまま
  読めなければならない（MUST）。
- **FR-014**: 新しい欄が無い状態に対する挙動は、この変更の前と一致しなければならない（MUST）。
- **FR-015**: すべての新しい配列は §10 の `arrayItems` と同じ上限を持たなければならない（MUST）。
- **FR-016**: 契約 hash・fixture・別言語実装が読む期待値は、この変更に合わせて再生成され
  なければならない（MUST）。手で書き換えてはならない（MUST NOT）。
- **FR-017**: 正本（addendum）の §4.3 の文面は、実装がとる扱いと一致しなければならない（MUST）。
  食い違ったまま残してはならない（MUST NOT）。

### Key Entities

- **開いている operation の記録**: 一致づけを待っている呼び出し。いまは識別・分類・状態・
  開始時刻・証跡 event の一覧を持つ。ここに「start の取り込み連番」「start の turn 由来」
  「受理した terminal の指紋」が加わる。
- **消えた証跡の記録**: 状態の live な集合から外れたもの。2 種類ある。(a) 上限で退避された
  operation、(b) 相手のいなかった terminal。どちらも識別と分類だけを持ち、内容は持たない。
- **契約の hash 一覧**: schema と fixture の生バイトの hash。別言語実装が同じ契約を読んでいる
  ことを確かめる唯一の手段。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 状態と event だけを渡された実装が、event store を持つ実装と、パリティ用の
  fixture 全件で**同一の**受理・隔離の判断、同一の状態、同一の内容 hash に到達する。
- **SC-002**: §4.3 が課す 3 つの検査すべてが、状態の外側の索引なしで実施できる（現在は 1 つが
  実施不能、1 つが部分的）。
- **SC-003**: 新しい欄を持たない既存の状態に対する挙動が、**#35 / #39 / #43 / #44 が名指しした
  欠陥の修正を除いて**、この変更の前後で変わらない。除外はこの 4 件が「現行の挙動が正本に
  反している」という報告そのものなので、挙動を保つと欠陥を仕様として固定することになる。
  **判定は変更前の実装との突き合わせで行い、除外は issue 番号ではなく具体的な差分で列挙する**:
  旧形（新しい任意欄を 1 つも持たない）状態と event の corpus を、変更前の実装（この branch の
  分岐点）とこの実装の両方に通し、結果が食い違う JSON path を 1 つ残らず許可表に挙げる。
  許可表には case 名・event・path・**そのときの値**・issue 番号が入り、表に無い差分が 1 つでも
  出れば不合格、表にあるのに差分が出なくなっても不合格とする。行数や書き換えた期待値の件数は
  この判定に使わない（数え落としても緑のままになるため）。**比較面は還元結果の全体**とし、
  診断・履歴・台帳を件数や code に縮約しない。**主張は corpus の範囲に閉じる**: corpus が
  届いていない経路は理由付きで列挙し、「全経路で変わらない」とは言わない。
- **SC-004**: 追加した規則ごとに、それを壊す変異が用意され、変異テストの生存が 0 件を保つ。
- **SC-005**: 状態のサイズが、どれだけ event を流しても上限で頭打ちになる（記録の追加によって
  上限が破られない）。
- **SC-006**: 正本と実装の食い違いとして残っている 4 件（#35 / #39 / #43 / #44）が、いずれも
  「実装が正本どおり」か「正本が実装どおりに直された」のどちらかになる。

## Assumptions

- 凍結 schema の変更は 1 回にまとめる（利用者の指示）。この spec の範囲で fixture と契約 hash を
  作り直す。**型名の版は上げず `schemaVersion` も `1` のまま据え置く**（`research.md`
  「型名の版を上げるか」の Decision。理由は、版を上げると `ContinuationCheckpointV2` から連鎖して
  checkpoint 自身の版まで動くのに、読み手がまだ 1 つも存在しないこと。drift の検出は版番号ではなく
  `harness/contract-hashes.json` が担う）。以後の追加も同じ判断基準で扱い、**本物の V2 が要る条件**は
  `plan.md` に明記してある。
- 新しい欄はすべて任意にする。既存の状態を移行なしで読めることを優先し、必須化はしない。
  必須化すると、この版より前に書かれた checkpoint が読めなくなる。
- 記録の上限は既存の §10 `arrayItems`（256）と同じ値を使う。別の値を選ぶ根拠が無く、
  値が分かれると上限まわりの規則を 2 通り持つことになる。
- 「消えた証跡」2 種類（退避・孤児）を 1 つの配列にまとめるか 2 つに分けるかは設計判断として
  plan 段階に送る。仕様としてはどちらでも SC を満たせる。
- Rust 側の実装はまだ無い。パリティは契約 hash と fixture で担保し、実コードの照合は
  Rust 実装が入った時点で行う。
- 退避を「誰が起こせるか」の制限（#45）はこの範囲外。ここで決めるのは**何が残るか**であって、
  誰が退避を起こせるかではない。

## Out of Scope

- 退避を引き起こせる主体の制限（#45）。intake 層の責務で、別件。
- lineage をまたぐ状態の順序鍵（#53）。この spec は 1 つの状態の中の順序材料だけを扱う。
- `unknown` のまま滞留する operation の寿命・期限（#39 の 3 つ目の箱）。記録の置き場ができた
  ことで扱いが変わりうるので、置き場を作ってから別途決める。
- 孤児 terminal の再送打ち切り（delivery 層の責務として evidence §2.10 に記録済み）。
