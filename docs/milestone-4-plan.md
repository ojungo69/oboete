# Milestone 4 (Deliver) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> **Depth, as in milestone 3's plan:** every decision and every task's files, interfaces and step bodies are here. Tasks 0-4, which settle the delivered set, where imported history lives and the search core that the rest builds on, got their step bodies first. Tasks 5-12 got theirs in this follow-up PR, written against the code of Tasks 0-4 and with the names that code uses.

**Goal:** What milestone 3's curator makes reaches the agent the way claude-mem's memory does (owner decision 31): at SessionStart, after compaction, and, once its line passes, at each prompt; and the past can be searched on MCP, CLI and the viewer, over claims, imported history and raw records. The evaluation store moves to Design B's schema, so that the single test-split run measures B's code. The tools that the owner's cut-over runs are built here (spec 7.5).

**Architecture:** Hooks only read (spec 4.1). The worker keeps the manifest per checkout, a shortlist per (session, checkout), the full-text indexes and the vectors. The hook reads the manifest row and the delivered claims, and it never waits on the network. "Delivered" (spec 3.4) is one query beside the chain tips, which curation keeps reading unchanged, and one pair rule places it on every surface. Imported history (claude-mem, v1's documents) is a new op type in raw.db, so it is backed up now and syncs later like other content ops (spec 5.4). A new consumer indexes it in knowledge.db. Search is one entry point that CLI, MCP and the viewer call. Vectors are made by a worker phase whose own thread calls the embedder, outside every database transaction.

**Tech Stack:** Rust (edition 2024), rusqlite (bundled SQLite, FTS5 trigram), sqlite-vec 0.1.9 (already a dependency), ureq for Workers AI, fastembed with a static ONNX Runtime behind the `local-embed` feature (Task 10), no async runtime outside MCP's rmcp (`src/mcp.rs`), and none added.

**Spec:** `docs/spec.md` 3.4, section 4 (all), 5.4 (imported documents), 5.5 (a query that leaves the machine), 6.5, 6.6, 7.1 (local embeddings), 7.4, 7.5, 8.1, 8.2 (M1, Raw, Rerank, M5, M6, Inject, M21, M22, Read hook, Transcript), 8.4 row 4, Appendix B rows 30-1, 30-2, 30-14, 30-16, 30-18, 30-22, 46-1 to 46-3, 50c-a and 50c-b, 53-1 to 53-6, 54-6, 55-1, 55-5 to 55-8; MUST-M8, M9, M11, M12, M13 (docs/research/redesign-2026-09-24/improvements-synthesis.md:126-220); issue #295 rows 1-3; owner decisions 31 and 32. What milestone 3 left: `docs/milestone-3.md`.

## Global Constraints

- Hooks never wait on the network and never embed a query. No reranker or judge runs in a hook (spec 4.1, 4.3).
- Only delivered claims (spec 3.4) are injected, never prompt text. A correction may name a claim no longer delivered by its id, date, kind, first words and what changed (its new status, or the later claim that ended it), and a claim the worker has not applied a change to (`claims::Pending`) only by its id (spec 4.8, A102). Every injection is fenced as data (spec 4.4, 4.6, 6.5; row 30-18).
- Hook state files (`state/hooks`) hold uids, fingerprints and record seqs, never memory text, so a tombstone or milestone 5's forget has nothing there to reach.
- Imported memories are for search and timeline only, never injected and never current (spec 4.5).
- The chain tips (`claims::TIPS`) stay the store's current state. Curation, digests and `anchored_through` keep reading them unchanged (spec 3.4).
- The new version never writes the old store (spec 7.4). `migrate` and the transcript import open `oboete.db` only through `migrate::open_v1` (`SQLITE_OPEN_READ_ONLY`, not `immutable`), never through `db::open`, and doctor does from Task 9 Step 2 on. `oboete eval`, `oboete reindex`, the viewer and doctor still call `db::open` until Tasks 6 and 7, the v1 tail's removal (D7) and Task 9 Step 2 take them out: until then none of them runs on a home that holds a v1 copy, since `ensure_device` rewrites a copied store's device id.
- Every reader opens raw.db before knowledge.db, so that a restore or rebuild swap waits for it (as `search::raw` does today).
- Every process that reads `vec_index` opens knowledge.db through `knowledge::open`, which registers sqlite-vec, so the worker, MCP, the CLI and the viewer read it without `db::open`. A hook reads no vectors: its read-only open in `consumer::manifest::text` stays outside this rule.
- Text sent to a remote embedder passes the egress gate and the exclusion check first (spec 5.5; rows 30-1, 30-2).
- A local model (bge-m3, the reranker) is loaded only by the worker and by processes that search, never by a hook, and no process serves it to another (D14; spec 4.10, A109).
- The test split is used once, for every retrieval candidate in one run (spec 8.1), pre-registered in `docs/eval/m4-prereg.md`, its own PR merged to main before any candidate runs; nothing is run again after the first grade. Held-out transcripts decide once. The deciding runs that read curated claims wait for milestone 3's deciding run (spec 8.4, A88).
- Per-prompt injection ships off by default until the Inject line passes (spec 4.6). The user may turn it on earlier (spec 1.5).
- Embedding spend has its own cap, outside the paid APIs' USD 5 a month (owner decision of 2026-09-27). `providers_db::usd_this_month` (`budget::admit`'s paid cap) leaves roles `embed` and `query` out; `embed_usd_this_month` backs `[embedding] monthly_usd` (default USD 1.0); `calls_in_a_day` for `workers-ai-embed` backs `daily_requests` (200), of which batches use at most 160 and the last 40 are kept for queries.
- The owner's machines keep running v1 until the cut-over after milestone 5. Design B runs only in the `oboete-dogfood` user and in temporary and evaluation homes (CLAUDE.md).
- Claude Code writes the core and every security-scope part: the delivered rule, the search core, the viewer's routes, the embedder's egress path, `migrate` (spec 8.4 "Who builds").
- CI: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test` on Linux, macOS and Windows. CI also builds and tests with `--features local-embed` on the operating systems where it builds. Builds this PC cannot make (Windows MSVC, macOS x64, Linux arm64) come from `local-embed.yml`, a `workflow_dispatch` job on main.

7. **Local embeddings on the 8 GB iMac.** Two agent sessions search while the worker embeds a backlog. Expected: no hook loads the model; each MCP process loads it on its first search, answers that one from full text, and drops it after 10 minutes without one; the worker loads it only past its threshold and drops it when nothing is pending; peak RSS of the three stays within spike line C (7.0 GB); a checksum mismatch or a changed byte leaves the provider as it was. ## Decisions

Each decision is Claude's unless marked otherwise, and the owner can overrule it. They settle what the spec leaves to milestone 4 or leaves open.

**D1. "Delivered" is one query beside the chain tips.** `claims::delivered(which, links_end)` in `src/claims.rs`, an SQL builder beside `TIPS`, returns the tips plus each claim `a` of kind decision or preference, active and decided, whose every inbound edge meets three conditions. The edge is a curator `supersedes` link. Its linker is active, not retracted, decided or done, and backed by the owner the way `anchored_through` already defines it (the user's own words, a proposal the user accepted, or a claim the owner corrected). The linker's `valid_from` is later than `a`'s. `TIPS` does not change. A retraction, an accepted proposal, a closed open item and an owner correction still end the older claim (spec 3.4).

The restatement links that recuration adds (`curate::restate`, #261) quote the same words of the same event, so their linker is never strictly later than the claim it links. They end a claim, as today, and never make one delivered, with no edge type of their own (#302 item 3; built in Task 1).

**D2. One pair rule for every surface.** Each surface ranks its own list of delivered claims. `claims::units` gives each claim of that list with the chain of later claims that ended it as one unit, the later claim directly before the earlier one, and `claims::place` fits whole units into the surface's places. The pair takes two places of the limit. If only one place is left, both go to the one-line index. Each claim is shown with its date. A constant `LINKS_END_DECISIONS` (false) is the switch that spec 3.4 waits for: once curator links pass M3's control line, the PR that records that result sets it, and the earlier claim then leaves delivery as it does from the tips (#295 row 1). It is a constant, not a setting, because it follows a measurement, not a preference. Every surface reads `claims::delivered`: SessionStart, the manifest, the shortlist, per-prompt injection, re-injection after compaction and search's first rank. Every surface that shows a limited number of claims places them with `units` and `place` (#295 rows 2-3).

**D3. The SessionStart packet's manifest part is stored; its delivered part is read (amends spec 4.1).** The worker keeps the manifest row per checkout, as it does today. The hook reads it, and it reads the delivered claims, the global preferences and the fresh digest from knowledge.db's indexes at SessionStart. It also reads the owner corrections that raw.db holds past the claims consumer's checkpoint and applies their status to what it shows, as the manifest read already checks tombstones not yet applied. So a claim the owner retracted since the worker's last run is never shown, and no packet rebuild is needed after each op (`consumer/manifest.rs` explains why decisions are read at SessionStart today). A stored packet replaces the live read only if M22's scale check shows that the live read pushes SessionStart past the read-hook line. The plan's first PR (#300) changed spec 4.1's first bullet to say so (A89). The per-prompt shortlist stays a worker product (D9), because its first stage needs vectors, which a hook never computes. The manifest's other-sessions line (MUST-M8: agent, branch, minutes ago, at most 5, the reader left out) and its `N events / T min not yet curated` (MUST-M9) are computed when the text is read, not stored, since T is measured at read time and a stored list keeps naming sessions as active on a checkout left idle. The stored ruleset carries a format tag, so rows built before are rebuilt at the worker's next pass (Task 8).

**D4. SessionStart's content, in spec 4.4's order.** It shows the explicit global preferences (`claims::global`); the manifest; delivered decisions, preferences, open items and lessons (kinds of spec 4.4; fixes, changes and repo facts are for search), about 10 with bodies, chosen by overlap with the manifest's files, last prompt and last failing command (so a lesson about the checkout's failing command gets its body, MUST-M21) and then by recency, and listed newest first (spec 4.4), the rest as one line each (`uid`, kind, date, first words); a line naming the `get`, `search` and `timeline` tools; the digest, only if fresh. A checkout with claims but no manifest row (a new branch, a dirty manifest, a tombstone not yet applied) still gets its preferences and delivered claims. Today it gets nothing.

**D5. Imported documents are `import` ops in raw.db.** Spec 5.4 says imported documents travel like other content ops, and raw.db's ops are kept, backed up and restored. A knowledge.db table alone would be lost on `rebuild`. So each document (a claude-mem observation, summary or prompt, or a v1 observation, summary or prompt) becomes one op of type `import`. Its body is `{uid, source, source_id, kind, repo, session, ts, title, body}`, at most 64 KB (`MAX_OP_BYTES`), with a longer body clipped with a marker. The source name is derived as `import.rs` derives it today, so that a document keeps its uid (`claude-mem:<hash>:o5`) and the 112-question judgments still map to it. The importer appends in batches bounded by count and by serialized size (under `raw::MAX_BATCH_BYTES`), each its own `batch`, and it reads the keys already imported before it appends, so a rerun appends nothing twice. A new op-log consumer, `Imported`, fills knowledge.db's `imported` table and its trigram `imported_fts`. Each row is keyed by the op that brought it, (device, op_seq), with the uid indexed, as claims are: a restore's rewind then removes exactly the rows of the lost ops, and a document that two devices imported stays once per op, shown once per uid. Curation reads records, not import ops, so it never sees them, and neither does injection. v1's observations, summaries and prompts become import ops too (Task 9), with source `oboete-v1:<v1 device_id>`, source ids `o<id>`, `s<id>` and `p<id>`, and v1's uid column (`<device_id>:<o|s|p><id>` when it is NULL). Rows v1 imported from claude-mem keep their own uid, and the once-per-uid display shows them once.

`OpKind` gains `Import`. `Raw::ops_after` refuses a type it does not know (`src/raw.rs`), so an older binary stops at the first import op. That is MUST-M17's version skew, parked at milestone 6. On one device, every binary that writes import ops also reads them.

**D6. Imported events are records, parked from curation.** v1's events (`source = oboete-v1`) and transcript events (`source = transcript`) become records on the local device with new seq numbers, as spec 7.4 says. Curation reads records by seq, and today it has no source filter. So when the curation phase reaches records of those sources, it writes a window op skipped with reason `imported:<source>` and sends nothing. The spans stay counted, which M2 needs (every seq is curated, elided or skipped with a reason). No window mixes live and imported records. `oboete recurate --source <source>` curates the parked spans, with a cost estimate first. For `oboete-v1`, the estimate lists first the sessions whose v1 render passed 16,000 characters (spec 7.4). The manifest's facts (last prompt and reply, failing command, files touched, other active sessions) come only from live sources, `hook` and `replay`: `replay` stands for live in the dev and evaluation homes. The not-yet-curated count leaves parked records out (spec 7.4, MUST-M9), and doctor counts them apart. The v1 import's checkpoint (the highest v1 event id imported, per v1 device) is an op of a new type, `migration`, body `{key, through, to_seq}`, appended in the same raw.db transaction as each batch of records, so that a backup carries it with them. v1's also holds `row`, the fingerprint (id, ts, session_id) of the event at `through`: v1's `events.id` is `INTEGER PRIMARY KEY` without AUTOINCREMENT, so SQLite reuses the ids of deleted newest events, and a pass refuses when the event at `through` is missing or differs from `row`, not only when v1's highest id is below `through`. Each pass and `--finish` also list the imported v1 sessions whose events no longer exist in oboete.db, so the owner can forget them in B (spec 7.4, A105; What needs the owner, item 15). The transcript import shares it, keyed `transcript:<agent>:<session>` through the last line; v1's key is `oboete-v1:<device_id>` (spec 7.4, A105). v1 events are read in id order and cut into batches by `IMPORT_BATCH` and `MAX_BATCH_BYTES`, each sorted by (ts, id). `Rebuild::finish`'s cascade treats a `migration` op past the restored records as it treats a window op, so a restore that lost a batch's records drops its checkpoint and every later op. v1's `session_repos` rows become records of kind `touch`, body `{}`, source `oboete-v1`, at the session's `started_at`, which survive a restore; the imported count, the transcript cut and the embedding phase leave them out. `migrate` never edits an existing `config.toml`; into a home that has none it copies v1's unchanged, and it prints what that file leaves unanswered (spec 7.4, A106). Until milestone 5's forget brings a deny-list, every importer calls `raw::denied`, which allows everything, and tests pin where it is called (spec 8.4, A104).

**D7. One search entry point.** `search::b::query(home, &Query) -> Result<Answer>` serves the CLI, MCP and the viewer and embeds the query itself (D8); `search::b::query_with(home, &Query, Option<&[f32]>) -> Result<Answer>` is the same search with a vector the caller made (Task 5). Delivered claims come first (D1, #295 row 3), then imported documents, then raw records (`RawArm::Below`), then lowered claims. Each leg fuses its own full-text top 100 and vector top 100 by RRF (k = 60: 1/(61 + rank), rank from 0 as in v1's `search::fuse`, ties in full-text order) (row 46-1; spec 4.10, A91). The imported leg keeps D2's hybrid shape (docs/pr-d.md; v1's `search::search` and `search::fuse`): its full-text top 100 is ordered knowledge before prompts, then by bm25, before the limit, split by kind, and each kind is fused with its own vector top 100, fused knowledge before fused prompts. That order also holds when the vector side is skipped. Its repository filter (`imported_repos`) also takes `claude-mem:<name>/…`, the name claude-mem gives a worktree session. Raw records rank below curated rows, the default that spec 8.2's Raw row keeps if its measurement cannot decide. Superseded, retracted and done claims rank below every delivered and current hit, labelled `superseded by <uid>` (or their status), and `history=true` removes that lowering (MUST-M11). `since` and `until` filter each leg before fusion, each document by its own time (MUST-M12). Every hit carries one label, `citable`, `quote-only` or `imported`, and a repository label (MUST-M13). MCP replies are fenced as data. A query that could reach a remote embedder is first checked against the exclusions of the caller's repository and of every repository searched (row 30-2; the list is D13's).

v1's readers leave main as their Design B replacements land. Task 4 removes MCP's and the CLI's v1 halves. Task 6 removes v1's `search::trec_run`, `outside` and `oboete eval --method`; its v1 baselines come from a `v1`-branch binary. Task 7 removes what only the viewer used: its v1 routes and two DELETE routes, `inject.rs`, v1 `search::{find, timeline, repos, session_docs, feed}` with their row types, `config::search_embedding` and `db::{delete_doc, delete_session}`. The rest of v1 (`search::{search, fuse, get}` with `hit`, `COLUMNS`, v1 `Hit` and `HYBRID_DEPTH`, `embed.rs`'s v1 functions, `oboete reindex`, and db.rs's `embeddings` and `vec_docs` schema) leaves in whichever of Tasks 5, 6 and 7 lands last (each has that step, taken only by the last): v1's `find` calls `fuse`, and `fuse` calls `get`, until Task 7. The owner runs the v1 branch's binary until the cut-over, and the cut-over's old-code search check runs that binary (spec 7.5 step 3), so main needs none of them.

**D8. Embedding is a worker phase with a thread of its own.** A consumer's step runs inside one knowledge.db transaction (`worker::pass`), so a network call cannot be a step: curation is a phase outside `pass` for the same reason (milestone 3's D3). The embedding phase covers claims, imported documents and raw records, because search runs its hybrid over all three (options-draft's Lookup: claims, raw chunks and claude-mem imports) and D9's shortlist needs claim vectors. It embeds a claim's corrected body, an imported document composed as v1 composes it (an imported uid's text is its row with the highest rowid), and a record's text as `raw_fts` indexes it, through `redact::outbound_lines`: each gated first, then cut (12,000 characters; a prompt 1,000), in that order of kinds. An imported document's title and body are also gated alone, as search gates them, with every view's masks found on the untouched text (`redact::outbound_joined`, as built in Task 6's first PR), so a rule anchored to a title holds and a rule on the composed text keeps its context. Records of imported sources (`oboete-v1`, `transcript`) get no vectors until the owner decides the cut-over's embedding cost (spec 7.4, A92). A document passed over is marked (`excluded`, `source`, `empty` or `refused`), so it never stalls a page.

Vectors are cached in knowledge.db by (embedder id, SHA-256 of the stored text), fp32 (`vectors`). `vector_keys` maps each document (claim uid, imported uid or raw `device:seq`) to its vector, and `vec_index` (vec0, bit[1024], partitioned by embedder and kind, with repo, time and session as metadata so that filters run before the KNN limit) is the searched index. A changed stored text or a changed embedder re-embeds; a changed egress rule does not re-embed a local vector, and a vector sent to a remote index is checked against the current rule when it is queued, at milestone 6 (spec 4.10, A94). So vectors survive `oboete rebuild` and a quarantine with no AI call (spec 1.7). `worker::rebuild` carries the cache from the set-aside file while it holds the worker lock, and a carry that fails fails the rebuild and keeps the file named. After a restore or a damage quarantine, the phase's first poll carries from the newest `knowledge.db.quarantined-*` into an empty cache; when that fails, the documents are embedded again within the cap and doctor's waiting line shows it. Only finite 4,096-byte unit blobs are carried, cache rows no key maps to are deleted once nothing waits, and mapping from the cache runs whatever the rest or the cap.

One call is in flight at a time, on a thread that holds no connection. Each poll reads a fresh page for one batch with no transaction open, so no text waits between polls. Right before sending, the thread opens raw.db, runs `curate::Reading::still`, closes it, then calls. The worker's loop writes the vectors in one short transaction, skipping any key whose stored text's hash changed meanwhile (row 55-6). The consumers and the curation phase never wait on that thread, so a held or failing call delays only the vectors (rows 55-1, 55-7). A sent batch's failure sets `provider_state` through `provider::next_state`, and doctor shows the retry time (row 55-5); a failure before any send (the exclusion list changed, a local error) and every query failure leave it alone. A 4xx other than 429 splits the batch, and a text refused alone is marked `refused` and shown in doctor. Outcomes are `ok` and `error` (a timeout is `error` with detail `timeout`), so `calls_in_a_day` counts every request that left. The phase runs before curation in each round of `serve`; a call in flight returns `Waiting` until its deadline, so the loop never spins. The worker stays up while the thread has work, as it does for curation's wait; with the local runner, work is a backlog at or past D14's threshold.

A generation is an embedder id: Workers AI and the local runner share `bge-m3`. With no generation yet, the first is active from its start. Only a change of embedder id builds a new generation, in the background. It becomes active when it covers every document that gets a vector (not excluded, not of an imported source, not empty or refused) (row 30-16; spec 4.10, A13; the remote index's drain comes with it at milestone 6), and undoing an exclusion queues its documents for the current generation (D13). Until then the query is embedded only by the active generation's embedder, which is no longer the configured one, so search answers from full text (`Skipped(Building)`). The old generation's rows are then deleted in pages. The first embedder is Workers AI's bge-m3, the model v1 uses. `[embedding] url` is a setting that loads only for the Workers AI host or a loopback address; anything else is a config error. Tests and Task 12b's harnesses point it at a stub, and the egress gate and the exclusion check run before every call whatever the URL. Calls are recorded in providers.db (`workers-ai-embed`, role `embed`) and counted against the embedding cap (Global Constraints; What needs the owner, item 1).

A query is embedded in two places, never in a hook: in `search::b::query` (MCP, CLI, viewer), on a scoped thread beside the full-text legs, with a 1.2 s timeout; and in the worker's shortlist phase (D9) through `embed_phase::Phase::ask`, which never waits. Either is recorded in providers.db with role `query` (readers now write providers.db; one that cannot open it skips the vector side unsent), counted in `daily_requests` from the 40 kept for queries, and skipped while `workers-ai-embed` rests or the cap is spent. It is embedded only by the active generation's embedder, and only while that is the configured one. `search::b::query` embeds with it; `search::b::query_with(home, &Query, Option<&[f32]>)` takes a vector the caller made: Task 6's evaluation passes precomputed vectors, and MCP and the viewer pass their process's local model's (Task 10). When the query cannot be embedded (off, excluded, no vectors yet, a new generation building, the embedder waiting, a timeout, an error), search answers from full text and `Answer.vector` says which (spec 4.10, A93); `oboete eval` treats anything but `Used` as an error.

A local runner of bge-m3 (spec 7.1) is built after a spike on its runtime (Task 10) and loaded as D14 says. It is accepted as the same model when its vectors agree with Workers AI's: a cosine minimum of at least 0.99 over at least 1,000 stored evaluation vectors stratified by length, language and kind, and a top-10 overlap of at least 9 over that sample for every one of the 312 dev queries, local over Workers AI documents and local over local, on each owner machine that offers `local`; the CI-only targets are checked on a public 200-text fixture against the same lines. So it is a deployment, not a retrieval candidate. The single test-split run uses Workers AI (D10).

**D9. Per-prompt injection and the shortlist.** A worker phase, like the embedding phase (D8), keeps at most 50 delivered claims per (session, checkout) under `claims::DECIDED` (spec 4.4's kinds, decided, or open items not done), the filter SessionStart uses, so no proposal and no done open item is injected per prompt. It builds shortlists only while `[inject] per_prompt` is on, and only for this device's sessions with a live event in the 30 minutes before now and no end (`ACTIVE_MS`) (spec 4.1, A100). It rebuilds a key after a `reply` (each Stop), every 20 events, after a rewind, and when the session moves to another checkout (a new key; spec 4.1), reading these triggers from `manifest_facts` with no new consumer, at most 8 keys a call. 20 stays until the dev harness for Inject shows a better value; the rebuild on sync comes with milestone 6. The shortlist's query has three parts, each gated with the current rules: the session's last 3 prompts on the checkout, its files touched, and its failing command (tool and `what_ran`, no output). `search::b::delivered_ranked` runs one full-text list per part (each within `search::trigrams`' 64) and fuses them with the vector list by RRF. The search runs outside every transaction, and only its result is written, in one short transaction. The vector is asked of the embedding phase through `embed_phase::Phase::ask` (D8), which never waits, only when `Raw::sessions_in` over the exclusion list holds no `agent\0session` of the key (every repository the session touched, a stricter rule than `search::b::excluded`), and at most once per key every 15 minutes (`VECTOR_EVERY`, pending the owner's answer on item 1). A vector whose text changed meanwhile is dropped, and while the embedder waits the shortlist is built from full text alone. Until the owner answers on spec 4.1's reranked and judge-scored stages (What needs the owner, item 12), only the first stage, plain hybrid RRF, is built.

At each prompt the hook matches two texts against the shortlist: the prompt after `strip_blocks`, and a failed call the session recorded since its previous prompt, so that a lesson about that failure comes back mid-session (MUST-M21; spec 4.2, A101). A body scores by the share of a text's trigrams it holds (`trigrams_upto(text, 256)`), which does not move with the store as bm25 does. Hits go through the pair rule (D2) into 3 places, and each is checked to be still delivered before it is injected (D3). `THRESHOLD` starts at 0.5, is set on dev questions in Task 8 and tuned in Task 12b; the Inject line, whose run waits for milestone 3's deciding run (A88), decides only `per_prompt`'s default. Until then `[inject] per_prompt` is off by default. `[inject]` also gains per-prompt and correction sizes and switches (spec 1.5), and the settings page shows them.

A correction is a claim shown to the session (with its body or as an index line) that is since retracted, done, no longer delivered, ended by a later claim (shown as its pair, later first) or corrected in body. It is named once, at the next prompt (spec 4.8), by id, date, kind, first words (80 characters, gated) and the change (A102). A claim hidden since by `claims::Pending` is named only by id, as withdrawn, and named again only if it comes back delivered. The shown set (uid to fingerprint, body or index line) is one hookstate value changed under the session's lock. It holds only what survived every cut; each SessionStart text replaces it and a resume keeps it; a claim shown only as an index line may still get its body per prompt; OpenCode's per-prompt uids stay out of it, because its context hook pushes them for one turn. `correction` is on by default, so every prompt after a SessionStart that showed claims reads knowledge.db, and the read-hook line is set with it on.

OpenCode context handoff (2026-10-02, #340): the plugin ignores the SessionStart capture's stdout, so that capture does not update shown state. The SDK reads its manifest with `inject --json --session`, sharing the plaintext path's read and gates; both this packet and prompt corrections carry an opaque `oboeteReceipt`. Only after pushing a packet into SDK system context does the plugin send `hook opencode ContextInjected` with `{session_id, receipt}`. The shown value holds at most 32 pending receipts for `hookstate::KEEP`, with uid, fingerprints and flags only, never packet text. A manifest receipt replaces the entire shown set and invalidates every older receipt, including when a nonempty packet shows no claims. A correction receipt applies under the same session lock where its before-entry still matches, or reaffirms an already-matching after-entry; it invalidates older manifest receipts completely and older correction changes for those uids, including A-to-B-to-A cases. Unknown, repeated, expired or superseded receipts do not advance shown state; a dropped packet or ACK may cost another notification. Plaintext `inject` and other agents keep their existing accounting. No model API acknowledgement is required.

The prompt point is UserPromptSubmit for Claude Code, Codex, Pi, OpenCode and Cursor, and agy's PreInvocation that recorded a prompt. Grok's UserPromptSubmit keeps the picked uids, and its next PreToolUse renders them with the corrections (a correction reaches Grok by a flag and its next tool use, spec 4.8). Grok, agy and OpenCode re-inject after compaction, as Claude Code, Codex, Pi and Cursor already do: Grok's PostCompact sets a flag taken at its next PreToolUse, agy re-injects after a `CHECKPOINT` past its first `PLANNER_RESPONSE`, and OpenCode drops its cached context on `session.compaction.ended`. Cursor's SessionStart is claimed once per conversation. Envelopes get nothing; prompts another agent sent are treated as typed. The recording-failure line stays at today's injection points. Cursor's blocks are each cut at a line to fit 9,500 units before they are joined, so no fence is cut. A static per-agent table records each point as live-verified, implemented or unverified (spec 4.7); v1's live checks of 2026-09-24 do not count as live-verified.

Each migrate pass and `--finish` list the imported v1 sessions whose events no longer exist in v1, so the owner can forget them in Design B (built in milestone 5, available at the cut-over). Claude proposes deleting nothing in the v1 viewer after step 2 and using that list and Design B's forget instead (spec 7.4, A105).
16. **M22's scale home disk.** The spec asks for a year of raw. Estimated from ov-B1 (70,904 records: raw.db 322 MB, knowledge.db 912 MB), a year (about 1.47 million records) takes about 34 GB inside WSL for a while, and WSL's virtual disk (vhdx) keeps that space on Windows until the owner's compaction script runs (administrator PowerShell). Claude proposes building 90 days (about 10 GB) first, measuring, estimating the year from it, and asking before building the year; large files are deleted right after the run, and only small result files stay. M22's query embeddings on real Workers AI are about 120 calls, each well under one neuron: USD 0, no waiting days.
17. **Subscription curation for the dev harnesses** (Task 12a). Measuring M6 and M5 needs a home with all 30 dev sessions curated from the start (ov-B1 curated only 70 spans). The estimate is about 29 million tokens (30/63 of the 60.43 million milestone 3 measured for the whole dev set), and M5's cut sessions at most as much again. Claude proposes the subscription Haiku, as in milestone 3's runs: no bill (owner decision 30), no paid curator, so the USD 5 cap is not touched. It takes a few days of the subscription's allowance, split over days when it hits the limit. The home is reused as the Window sweep's default-size point.
