# PR-E0 — 強いほうの全文検索 (2026-09-24)

PR-B2 の結果 (`docs/pr-b.md`) で、今の全文検索 (空白で区切った語の AND) は日本語の問いでほぼ役に立たないとわかった (dev の hit@10 0.086)。提案 §7 の PR-E0 の行として、`search::search` を置き換える。§3.3 の「意味検索が全文検索だけに比べ +0.03」の比べる相手は、この版にする。

## 変えたこと

- 問いを空白と句読点で区切り、各部分を 3 文字ずつずらした断片 (trigram) に切る。全部ひらがなの断片 (「をして」「ください」など、ほぼどの日本語の文書にもある) は捨てる。重複を除き、最大 64 個。
- 断片を OR でつなぎ、FTS5 の bm25 で並べる。多くの断片、特に珍しい断片を共有する文書が上に来る。知識 (観測・要約) が先、prompt が後なのは今までどおり。
- 断片が 1 つも取れない問い (`db`、`接続` のような 2 文字以下の語だけ) は、今までどおり語ごとの LIKE の AND。
- CLI の `search`、MCP の `search`、viewer は同じ関数を使うので、全部この版になる。

## 候補の比較 (spike)

評価用の store (約 18 万件) で、問いの切り方を 7 通り試した。数字は判定済みの文書だけで並べ直した値 (condensed list) で、新しい方式の上位 10 件のうち判定済みは 1〜2 割しかないため、候補を絞るためだけに使った。

| 方式 | nDCG@10 (目安) | 1 問の時間 p50 / p95 |
|---|---|---|
| 語の OR (3 文字以上の語だけ) | 0.188 | 8 / 341 ms |
| 漢字・カタカナ・英数の語 | 0.284 | 48 / 429 ms |
| 全部の trigram | 0.319 | 312 / 976 ms |
| **全部ひらがなを除いた trigram (採用)** | **0.327** | 302 / 965 ms |
| 珍しい順に 32 個 | 0.296 | 144 / 662 ms |
| 珍しい順に 16 個 | 0.273 | 28 / 418 ms |
| 5% を超える文書に出る断片を除く | 0.279 | 36 / 202 ms |

最も良かった形を Rust で書き、`oboete eval` の出力 (`e0-trigram`) を判定にかけた。断片は索引と同じく大文字小文字を畳んでから重複を除く (`HTTP http` で同じ断片を 2 回数えない)。

## claude-mem の既定の検索は 90 日より古い記憶を返さない

claude-mem の検索は、Chroma の上位 100 件から「今日から数えて 90 日より古いもの」を捨てる (`SearchManager.ts`、13.25.3)。dev の問い (developer の prompt) 265 問のうち 199 問は 90 日以上前に打たれたもので、答えの多くは 90 日より古い。この作りのまま測ると、claude-mem の値は「検索の質」ではなく「窓の外にある記憶は見えない」ことを測ってしまう。

`/api/search` に `dateStart` を渡すと窓が置き換わる (`dateStart=2026-01-01&dateEnd=2026-03-01` で 1〜2 月の観測だけが返ることを確認)。そこで claude-mem を 2 通り測った。

- `claude-mem`: owner が今使っている既定の検索 (90 日の窓あり)。
- `claude-mem-nowindow`: `dateStart=2000-01-01` で窓を外したもの。Chroma の上位 100 件はそのまま。

決定 22 (oboete の既定の検索が claude-mem を下回らない) は、強いほうの `claude-mem-nowindow` と比べる (提案 §3.3 に追記)。

区画の意味 (文書を除く区画では、各方式の判定済みの上位 20 件の中で除いて繰り上げる。20 件より下の判定していない文書を「関係なし」として繰り上げないため。除かれる文書が多い方式ほど 10 件に満たなくなり、不利になる向き):

- **90 日以内 / 以前に打った prompt**: 90 日は claude-mem の run を取った時刻 (`runs/claude-mem.trec` の更新時刻) から数える。claude-mem の窓もその時刻から数えているため。
- **問いより前に書かれた文書だけ**: 問いを打った時点の検索が見られた文書に絞る (未来の文書を答えに数えない)。問いの時刻が分かる developer の prompt だけ。
- **問いを引用した文書を除く**: 問いの trigram の 8 割以上を含む文書 (別の会話の要約が「Request: …」として問いを写しているものなど) を、run と正解の両方から除く。字面が同じ文書は全文検索に有利なので、それを除いても差が残るかを見る。今の AND が当てていたのはほぼこれだけだった。
- **観測だけ**: claude-mem の run は観測しか返さない (`type=observations`) ので、oboete の要約と prompt を除いて同じ土俵にする。

## わかったこと

- trigram の OR は、どの区画でも今の AND を大きく上回り、窓なしの claude-mem も上回る (英語の問いは同等)。claude-mem の埋め込みは英語用の all-MiniLM-L6-v2 で、日本語の問いに弱い。
- owner が今使っている claude-mem の既定の検索は、窓のせいで dev の答えの多くを見られない (hit@10 0.418 対 窓なし 0.617)。
- 決定 22 の線は、dev ではこの PR で越えている。合否は PR-D 以降に test 分で 1 回だけ測る (§3.3)。
- 意味検索 (PR-D) の合格線「全文検索だけに比べ +0.03」の相手は e0-trigram (dev の nDCG@10 0.557)。

## 限界

- 判定器 (sonnet) の信用はまだ測っていない (B3 の人の正解 50 組)。LLM の判定器は字面が重なる文書を高く付けやすいと言われる。「問いを引用した文書を除く」区画で差が残ることは確かめたが、人の正解で順位が同じになるかは B3 で見る。
- 窓なしの claude-mem は、Chroma の上位 100 件を日付で絞る作りのまま。問いの時点の claude-mem (その時点の文書だけで上位 100 件を取る) とは少し違う。
- test 分は開けていない。

## 速さ

CLI の `oboete search --all` (起動を含む)、評価用の store (約 18 万件) で dev の問い 100 件:

| | p50 | p95 | 最大 |
|---|---|---|---|
| 今の AND | 11 ms | 45 ms | 263 ms |
| trigram の OR | 308 ms | 767 ms | 1,288 ms |

MCP 検索の予算 (最も遅い端末で p95 1.5 秒) には収まる。M1 iMac では未計測。今の普段の store は数千件なので差は小さいが、claude-mem を取り込む PR-H の後はこの数字になる。記録 hook は検索を呼ばないので変わらない。

prompt ごとの自動注入 (PR-F、予算 300 ms) には重い。そこでは spike の「5% を超える文書に出る断片を除く」(p95 202 ms) か「珍しい順に 16 個」(p95 418 ms) のように断片を絞る形を、PR-F の評価で選ぶ。

## 再現

```sh
cd docs/eval
# e0-trigram: この PR のビルドで
oboete --home ~/.oboete/eval/home eval ~/.oboete/eval/queries.jsonl --depth 50 | sed 's/ fts$/ e0-trigram/' > ~/.oboete/eval/runs/e0-trigram.trec
python3 run_claude_mem.py --no-window        # runs/claude-mem-nowindow.trec (約 21 分)
python3 judge.py dev 312                      # 600 回ごとに止まるので、0 件になるまで繰り返す
uv run --with ranx python report.py dev
```

`runs/fts.trec` と `runs/claude-mem.trec` は PR-B2 のもの (`fts` は置き換え前の AND)。
