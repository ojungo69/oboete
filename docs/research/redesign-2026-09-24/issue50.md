# Issue #50 (owner, 2026-09-24 20:13)

## 要旨

**推奨：Hindsight本体への置き換えではなく、oboeteの要件を最上位に置いたRust＋SQLiteの記憶基盤を作る。Hindsight／Mastra／Graphiti／claude-mem等から、要件に適合し効果を検証できる仕組みを取り入れる。**

ownerの依頼（2026-09-24）：「ベースをhindsightにした理由は精度？」「oboeteで作りたいものを無駄なもの以外切り捨てない前提で設計を考えてもそうなる？」「自信をもってその設計を出せるならissueを立てて」。本Issueはその再検討結果。

- Hindsightの公開成績は比較候補にする理由にはなるが、oboeteの日本語開発記録・同じ回答モデル・同じ予算で勝つと実測したわけではない。**Hindsightの部品を採用すれば、その製品全体のベンチマーク成績を引き継げるという主張はしない。**
- 「Hindsight型」は、根拠を持つ個別知識と、更新可能な派生要約を分ける設計上の参考という意味。fork／実行時依存／全面Rust移植を既定路線にはしない。
- **機能削減による軽量化はしない。** 軽くする対象は重複処理、不要な再生成、無制限の再試行、不要な索引・サービスの二重化。重いという理由だけで有用な機能を「無駄」に分類しない。
- 構築方法はクリーンな再設計でもよいが、既存の有効なアダプター・provider・redaction・検索・テストを捨てる必要はない。
- 本Issueは設計・受け入れ条件の親Issue。作成だけで本番変更、claude-memの停止、既存データ削除、有料サービス追加を許可するものではない。実装詳細は既存の軽量なPRプロセスで詰める。

## 3. なぜHindsight本体を必須の土台にしないか

| 案 | 利点 | この要件集合での判断 |
|---|---|---|
| Hindsightをfork／必須バックエンドにする | 既存の検索・知識統合・Mental Modelsを利用できる | 比較候補として有力。ただしPostgreSQL中心の保存と、oboeteのSQLite・端末処理・Cloudflare同期の組合せには適合作業が必要。日本語引き継ぎ品質・総コストで勝つという実測なしに移行を決めない |
| **oboete要件中心のRustコア＋選択的な設計・部品の採用** | 全要件を一体で満たす契約、失敗時の動作、同期と権限制御を設計できる | **推奨**。自作分の設計・検証責任を引き受ける。既存資産が惜しいからではなく、要件適合性を理由に選ぶ |
| oboeteとHindsightの二重メモリを常時運用 | 両方の能力を試せる | 比較試験にはよいが、正本・削除・秘密・費用・注入が二重化するので製品の既定構成にはしない |

HindsightはPostgreSQLを主要保存先とし、汎用のstorage抽象を設けない方針を公式に説明している：[Storage](https://hindsight.vectorize.io/developer/storage)。ローカル実行ができない、必ず有料APIが必要、という理由で退けているのではない。

**再判断条件：** 同じ要件・データ・モデル／予算条件でHindsight基盤の方が明確に品質と運用を改善し、R01〜R16を失わずに満たせる証拠が出たら、コード基盤の選択は見直してよい。推奨構造を守るために性能で劣る実装へ固執しない。

## 4. 推奨する記憶の契約

### A. 元の記録・根拠層

- agent/device/sessionとソース側の順序・出典を持つ、秘密を除いた記録を保存する。別経路で同じイベントが届いても二重化しない。一方、文面が同じというだけで別の出来事を消さない。
- 大きな会話をイベント／チャンク単位で順に処理する。各ジョブが読んだ範囲、確定した範囲、再試行状態を記録し、**要約器に一度も渡していない中央部分を成功扱いで捨てない**。
- 知識の保存と処理済み範囲の確定は同じトランザクションに置く。処理中のクラッシュ・再実行は冪等にする。モデル呼出し自体のexactly-onceを約束するのではなく、記録の欠落や二重確定を防ぐ。
- 通常の保存失敗と処理待ちを区別する。ディスク満杯など物理的に保存できない場合に「記録済み」と表示しない。取得可能なtranscriptからの回復と警告を用意し、存在しない上流ログからの完全回復は保証しない。
- 長期知識の根拠になる短い引用・発言者・出典ID・時刻は保持する。raw全文の保持期間は既存仕様の不整合を整理して明示する（planの保持記述と現在の即時削除は同じではない）。未処理データの自動破棄はしない。生ログ永久保存や無制限の容量増加を既定にもしない。
- rawの削除後は、保持した根拠だけが検証可能であることを表示する。全文からの再抽出ができるふりをしない。

### B. 個々の知識・状態層

名称やテーブル分割は実装PRで決めるが、次の情報は表現できること：内容／種類／出典／発言者／適用repo／必要な場合のbranch・commit／発生時刻と記録時刻／提案・確定・検証結果等の状態／訂正・置き換え関係。

- ユーザーの選択、AIの提案、ツールが確認した結果、AIの推測を混ぜない。
- ユーザー引用の部分一致は「引用がそこにある」検査であって、承認の証明ではない。質問・否定・転載・仮定と、本当の承諾を区別する。曖昧ならproposed/unverifiedとして保持する。
- 実装完了の自己申告と、特定コード状態に対する検証結果を区別する。テストの成功を全branchへ永久適用しない。
- `why`は根拠があるときだけ保存し、なければunknownを許す。理由不明というだけで有用な変更事実まで捨てない。「N行変更」だけのノイズとは区別する。
- 旧形式・import記憶に確認済みの証拠を捏造しない。検索可能性を保ち、確定性や出典の限界を表示する。既存K1の旧形式の扱いと異なるため、互換性の差分を明記する。
- 新しい確定事項が古い事項を置き換えるときだけ、対象範囲を確認して`supersedes`相当の関係を追加する。似た話題だけでは置き換えない。新しい提案で確定事項を消さない。
- 同期で表現が収束することと、内容の正しさは別。既存rev規則を維持しつつ、同時に生まれた矛盾する主張は到着順だけで正解を決めず、競合として扱えるようにする。
- 明示削除と、履歴を残す「現在は無効」を分ける。古いという理由だけで有用な知識を自動失効させない。

### C. 現在の引き継ぎ・話題別要約層

- 個別知識から生成する派生物とする。要約文が唯一の正本にならない。
- 「現在の方針」「作業の再開」「未解決事項」「プロジェクトの慣習」などを、必要なものから作る。汎用Wiki、別のissue tracker、agent orchestratorを作る話には広げない。
- 各表示ブロックに根拠ID/版と適用scopeを持たせる。話題の新規情報も検出するため、引用済みIDだけでなくscopeの更新位置も追う。
- **追加・訂正・無効化・削除・共有範囲変更で更新待ちにする。** 削除や公開範囲の取り下げでは、再生成を待って古い文章を配り続けない。
- 再生成中に根拠が変わったら、その古いスナップショットの結果を現在版として上書きしない。トランザクションと版の比較で公開する。新しい情報が未処理なら、見ていないのに最新扱いしない。
- 更新待ち時は有効性が確認できる個別知識と状態表示へ戻る。古いセッション要約を「現時点の決定」として代わりに注入しない。履歴として読む入口は残す。
- 人間の訂正も版付きの変更として保存する。viewerだけ直ってMCPや別端末は古いまま、を認めない。

HindsightのMental ModelsはこのC層の良い参考だが、完全な答えではない。調査時点の[公式API資料（固定commit）](https://github.com/vectorize-io/hindsight/blob/d94c3d83b297a6298f1a1abc35fc82f9c9b9d5ce/hindsight-docs/docs/developer/api/mental-models.mdx)は、**削除だけではstalenessが立たない**ことを明記している。oboeteではこの挙動をコピーせず、削除・除外までを契約に含める。

## 5. 検索・自動注入・providerを一体で扱う

### 検索と注入

- 通常の検索は生成LLMを必須にしない。FTSと意味検索を融合し、明示時期・識別子・適用範囲で補う。RRFのスコアを正しさの確率と誤認しない。
- 「現在の方針」と「過去の経緯」を別の検索意図として扱う。現在の検索では置き換え済み事項が現在の決定を押しのけない。履歴検索では旧事項と変更理由を読める。`get`で旧事項を読む場合も状態が見える。
- SessionStartは少量の重要な確定制約・再開情報を本文で渡し、その他はID付き目次。重要制約を任意の検索に丸投げしない。
- promptごとの注入、compact後の再注入、resume時の重複回避、非永続contextを使うagentの再提示をアダプター契約として維持する。
- 注入対象は現在の規則どおり観測・要約等のデータ。prompt原文やimport記憶を無条件で自動注入しない。生成された引き継ぎ文を新しい独立証拠として再抽出しない。
- token予算・重複排除で省いた項目は保存から消さず、検索／getで取得可能にする。詳細取得も含めた総tokenと作業成功率で評価する。
- ファイル内容やツール出力に含まれる命令を、所有者のルールやglobal preferenceへ昇格させない。メモリはデータであり、新しい操作権限を与えない。

### providerと実行

- 通常の抽出は既存の順序付きchain。矛盾・重要な置き換え等の再確認は、既に許可されたprovider/modelと予算の範囲で必要時だけ行う。二重LLM確認を常時必須にはしない。
- providerごとの失敗・cooldown・日次予算・出力schema・上限を維持。通信失敗と意味的に判断できない出力を分け、判定不能を確定事項として保存しない。
- すべて止まっても元記録の保存と既存記憶の検索を続ける。整理待ち・同期待ちを隠さない。自動resumeの契機と手動の再試行経路を用意し、「次回」が永久に来ないpendingをdoctorで検出する。
- CLI実行の自己記録防止、promptを引数へ露出しないこと、本人設定・秘密の保護を維持する。
- 「ローカル保存」と「外部送信ゼロ」を同一視しない。完全ローカル構成では抽出・embedding・rerank等を含め外部通信ゼロを確認する。

## 6. 同期と削除は後付けにしない

- ローカルのみでは手元のSQLiteが記録の権威。クラウド利用時は各端末の元記録と、hubに確定した共有op／版を区別する。各端末のキャッシュを別々の唯一の正本と呼ばない。
- 既存のuid/rev/ack/tombstone設計と#30の条件を引き継ぐ。ベクトルは索引であって、記憶の正本ではない。
- 同期するのは承認済みの文書・prompt・ベクトル・必要な制御情報。知識の状態・訂正関係・派生物の根拠と版も一貫させる。根拠となる新しい引用フィールドの送信は既存の外部送信・除外規則を通し、raw全文の送信拡大へすり替えない。
- 内容変更・再索引・旧埋め込み世代・再送・復元・再importがあっても、明示削除を復活させない。
- 派生要約は参照した出典全体の秘密／除外条件を引き継ぐ。一部の許可された出典だけを見て、混ざった禁止情報を公開しない。
- 除外／失効確認が必要な外部処理で最新条件を取得できなければ外へ送らずpendingまたはローカル経路へ戻す。hub `/embed`の採否は§0.2の確認待ちのままにする。
- クラウド索引の更新が遅れても、検索の返却時にhubの有効性・権限・削除状態を再確認する。ローカルでも同じ原則。
- オフライン端末への瞬時の反映は約束しない。端末は既知の共有版と最終同期を表示し、再接続時に削除・除外を優先して反映する。破棄した内容を持つ古い端末が再送してもhubで復活させない。
- 内容を忘れるための明示削除では、原文、引用、派生本文、FTS、ベクトル等も追跡して除去する。復活防止に必要なtombstoneは本文を含まない形で保持する。バックアップからの復元にも同じ規則を適用し、オフライン媒体まで即時消去済みと偽らない。

## 9. 受け入れ条件

既存の§3.3や#30/#46の合格線を都合よく緩めない。新しい改善は単独と組合せの両方で測る。効果がない方式は置き換えるが、それで必要機能を削らない。

### 正しさ・復旧の回帰テスト

- [ ] 長い記録の中央だけに重要な決定／検証結果があるfixtureで取得できる。各チャンクを処理したことを確認できる。
- [ ] 要約途中の失敗、保存直前のクラッシュ、同時実行、重複イベント、再試行で、未処理が成功扱いにならず知識の二重確定も起きない。
- [ ] 「AIが提案」「ユーザーが質問／否定／引用」「ユーザーが明示承認」を区別する。単純に全部unverifiedとして正確さを稼がず、本物の決定のrecallも測る。
- [ ] 方針A→Bで、古いAが観測・要約・話題別表示・検索snippet・キャッシュのいずれからも現在の方針として復活しない。履歴ではAと変更根拠を読める。
- [ ] 新規知識、訂正、削除、scope変更、再生成中の更新で派生物の鮮度が正しい。古いworker結果が現在版を上書きしない。
- [ ] 別branchのテスト結果、別repoの決定、AI自己申告を不適切に横流ししない。repo全体に有効な方針は正しく共有できる。
- [ ] 要約の引用から秘密や除外repoの内容が漏れない。`search/get/timeline`、remote MCPのID直指定、`all`、Vectorizeの遅延を含める。
- [ ] 明示削除後の再同期・再index・再import・バックアップ復元で内容が復活しない。同期取り下げの解除は、明示削除とは区別して既存仕様どおり扱う。
- [ ] provider全滅／オフラインでも記録・既存検索は使え、新しい知識の整理待ちと復旧経路が分かる。
- [ ] 二重注入／compact／resume／自己記録ループをagentごとに確認する。正式なイベントや取得可能なtranscriptがない区間は未確認を隠さない。

### 品質・実用性の比較

- [ ] 記憶なし、比較時点の現行oboete、claude-mem（既定と90日windowを外した強い基準）、必要な比較構成のHindsightを区別して評価する。

- [ ] 日本語→日本語、日英混在、古いが有効な記憶、撤回、提案誤認、複数セッション、答えなし／誤った前提を含める。
- [ ] 同じ入力・回答モデル・利用できる記録時点を揃えた比較と、同予算下で各方式を最適化した比較を分ける。要約・埋め込み・rerank・回答の設定、commit、cache条件を記録する。
